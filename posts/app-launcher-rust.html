I Didn't Like App Launchers for Arch Linux, So I Wrote My Own in Rust

March 2026 6 min read

Three Launchers, Three Disappointments

Every Arch Linux setup eventually hits the same question: which app launcher do you use? The usual suspects are rofi, wofi, and fuzzel. I tried all three.

Rofi is powerful, but it carries years of accumulated config options and X11-era baggage. Wofi works on Wayland but has its own quirks and the theming story never clicked for me. Fuzzel is probably the cleanest of the three, but I kept running into small friction points — missing features I wanted, features I couldn't turn off, a color scheme that wouldn't quite match my terminal setup.

At some point I stopped fiddling with config files and asked myself: how hard would it actually be to write a minimal one from scratch? I had been using Rust for side projects, so the answer was obvious.

Five Requirements and a Free Weekend

My requirements were deliberately minimal:

  • Discover installed apps from .desktop files
  • Fuzzy filter as I type
  • Launch the selected program and exit immediately
  • A Wayland layer-shell overlay — centered on the active screen, no window chrome
  • Look exactly like the rest of my setup

Normally, a project like this would sit in the "someday" pile for months. Between researching which Wayland crates are production-ready, reading the freedesktop .desktop spec, figuring out how layer-shell surfaces work, picking a GUI framework and learning its model — that's easily weeks of evenings before you have anything running. I'd been through that loop before on other projects. Research, try, hit a wall, research again.

This time I paired with Claude Code, and the whole thing took a few hours.

The Build

I started with a straightforward prompt: scaffold a Rust binary that reads .desktop files, filters them with fuzzy search, and launches the selected app. No UI yet — just the core logic.

The AI produced a working skeleton immediately. The .desktop file scanning, the fuzzy matching wired to a filtered list, the exec field-code stripping (the freedesktop spec defines placeholder codes like %f, %F, %u, %U that need to be stripped before passing the command to a shell — not hard, but easy to miss if you haven't read the spec) — things that would have each cost me an hour of reading specs and docs came back in seconds. Not perfect, but runnable. I could poke at it right away.

From there the loop was fast: read the generated code, understand it, push on the next piece. "Now wire this into an iced window with a layer-shell surface." "The fuzzy sort should rank higher-scoring matches first." "Icons should fall back to the system theme if no embedded SVG is found." Each step built on the last without the usual detour into documentation rabbit holes.

The places where I had to slow down and think were the architectural decisions: committing to Wayland-only via iced_layershell, whether to scan .desktop files at startup or lazily, how to structure the event loop. Those choices were still mine. But everything between a decision and working code was dramatically compressed.

Under the Hood

The final stack is about as minimal as it gets for a GUI app in Rust:

  • iced + iced_layershell — Elm-inspired retained-mode GUI (model → update → view) running on a Wayland layer-shell surface (Wayland-only, no X11)
  • fuzzy-matcher — the SkimMatcherV2 algorithm, the same engine behind the skim fuzzy finder
  • freedesktop-desktop-entry + xdg — parse .desktop files and resolve XDG base directories
  • rust-embed — compile SVG/PNG icons directly into the binary so they're available even when the system icon theme is missing an entry
  • std::process::Command — spawn the selected app and immediately exit

Here's the actual search filter from app.rs:

fn apply_filter(state: &mut Trebuchet) {
    if state.query.is_empty() {
        state.filtered = (0..state.apps.len()).collect();
    } else {
        let matcher = SkimMatcherV2::default();
        let mut scored: Vec<(usize, i64)> = state
            .apps
            .iter()
            .enumerate()
            .filter_map(|(i, app)| matcher.fuzzy_match(&app.name, &state.query).map(|s| (i, s)))
            .collect();
        scored.sort_by(|a, b| b.1.cmp(&a.1));
        state.filtered = scored.into_iter().map(|(i, _)| i).collect();
    }
    if !state.query.is_empty() && !state.filtered.is_empty() {
        state.selected = Some(0);
    } else {
        state.selected = None;
    }
}

Each keypress re-scores all app names against the current query and sorts by score descending. The skim algorithm naturally rewards consecutive and prefix matches, so typing "fire" surfaces Firefox above anything that merely contains those letters scattered across the name.

What It Does (and Doesn't)

The launcher does exactly what I wanted and nothing more. I open it with a keybind, type a few characters, hit enter, and the app opens. A quick bash script timing the process puts cold start at 24ms — and the binary lands at 25MB with rust-embed baking the icons in. Neither number is surprising given the stack, but good to know. Closing without selecting does nothing.

What it doesn't do: remember history, weight frequently used apps, act as a file browser or calculator. All deliberate omissions. If I ever want frecency ranking I'll add it then.

The part I'm most happy with is the icons. Trebuchet sources them from multiple places — bundled SVGs compiled into the binary, the system icon theme, and absolute paths from .desktop files — with SVGs preferred over rasters. On a high-DPI monitor the difference is noticeable: every icon is crisp and correctly sized, no blurry upscaled PNGs. It's a small thing, but it's the kind of polish that makes a tool feel finished.

The window is fully transparent, so it sits cleanly over any desktop without fighting the theme. Keybindings are configured in your compositor — a single line in hyprland.conf is all it takes to bind it to a key.

Hours vs. Weeks

The honest version of this story without Claude Code: trebuchet never gets built. Not because it's technically out of reach, but because the research overhead would have kept pushing it to "next weekend." The Wayland ecosystem in Rust is still young — finding the right crates, understanding how layer-shell works, learning iced's architecture — each of those is a real time cost that adds up fast for a personal project with no deadline.

A few hours is a fundamentally different category than a few weeks. It means you can actually finish things. Scratch your own itches. Build tools that fit exactly how you work, instead of settling for something close enough.

The dynamic I found most useful: an AI coding assistant is fastest when the problem is well-scoped. "Parse .desktop files and return a list of app entries" gets an accurate result immediately. The architecture — what modules to split things into, which trade-offs to make — that still needs a human. But the gap between a decision and working code is now almost nothing. That's what makes the difference.

One last note: I'm relatively new to Rust, and most of the tech stack in this project — iced, Wayland, the freedesktop ecosystem — was unfamiliar territory. If you spot something that could be done better, I'd genuinely love to hear it. The code is on GitHub.

Oh, and I installed Arch Linux for the first time this same weekend. So apparently I'm an Arch user now, which means I'm contractually obligated to mention it.
