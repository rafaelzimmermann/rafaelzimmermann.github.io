I Didn't Like App Launchers for Arch Linux, So I Wrote My Own in Rust

March 2026 9 min read

Three Launchers, Three Disappointments

There's a certain irony in spending three hours configuring a tool whose entire job is to save you two seconds. App launchers for Linux are where that irony lives. You install one, read the man page, write the config, tweak the theme, and somewhere along the way forget you just wanted to open Firefox faster.

Every Arch Linux setup eventually hits the same question: which app launcher do you use? The usual suspects are rofi, wofi, and fuzzel. I tried all three.

Rofi is powerful, but it carries years of accumulated config options and X11-era baggage. Wofi works on Wayland but has its own quirks and expects you to bring your own CSS theme, which is not something I am used to, especially coming from Ubuntu. Fuzzel is probably the cleanest of the three, but I kept running into small friction points: missing features I wanted, features I couldn't turn off, a color scheme that wouldn't quite match my terminal setup.

At some point I stopped fiddling with config files and asked myself: how hard would it actually be to write a minimal one from scratch? I had been using Rust for side projects, so the answer was obvious.

rofi wofi fuzzel trebuchet
Wayland-native No (XWayland) Yes Yes Yes
Config required Yes (extensive) Yes Minimal None
Fuzzy scoring Yes Basic Yes Yes (skim)
SVG icons No No No Yes
Runtime dependencies Many GTK Few None (static)

Rough picture, not a benchmark. "Config required" means you need to write something before it looks or behaves the way you want.

Five Requirements and a Few Hours

My requirements were deliberately minimal:

  • Discover installed apps from .desktop files
  • Fuzzy filter as I type
  • Launch the selected program and exit immediately
  • A Wayland layer-shell overlay (centered on the active screen, no window chrome)
  • Look exactly like the rest of my setup

Normally, a project like this would sit in the "someday" pile for months. Between researching which Wayland crates are production-ready, reading the freedesktop .desktop spec, figuring out how layer-shell surfaces work, picking a GUI framework and learning its model. That's easily weeks of evenings before you have anything running. I'd been through that loop before on other projects. Research, try, hit a wall, research again.

This time I paired with Claude Code, and the whole thing took a few hours.

The Build

I started with a straightforward prompt: scaffold a Rust binary that reads .desktop files, filters them with fuzzy search, and launches the selected app. No UI yet, just the core logic.

The AI produced a working skeleton immediately. The .desktop file scanning, the fuzzy matching wired to a filtered list, the exec field-code stripping (the freedesktop spec defines placeholder codes like %f, %F, %u, %U that need to be stripped before passing the command to a shell; not hard, but easy to miss if you haven't read the spec), things that would have each cost me an hour of reading specs and docs came back in seconds. Not perfect, but runnable. I could poke at it right away.

From there the loop was fast: read the generated code, understand it, push on the next piece. "Now wire this into an iced window with a layer-shell surface." "The fuzzy sort should rank higher-scoring matches first." "Icons should fall back to the system theme if no embedded SVG is found." Each step built on the last without the usual detour into documentation rabbit holes.

The places where I had to slow down and think were the architectural decisions, and those were genuinely worth thinking about:

  • Wayland-only: Chose simplicity over compatibility. Hyprland is Wayland-only; supporting X11 via XWayland would add real complexity for zero personal benefit. If you need X11 support, this probably isn't your launcher.
  • Startup scanning: .desktop files are scanned once at launch. Since the launcher opens fresh each time, a 24ms startup includes scanning, which is acceptable. Lazy scanning would add complexity with no latency benefit after the first keypress.
  • Single state struct: All state lives in one Trebuchet struct. This matches iced's Elm model cleanly: one model, one update function, one view. Splitting state across modules would fight the architecture rather than use it.

Those choices were still mine. But everything between a decision and working code was dramatically compressed.

Under the Hood

The final stack is about as minimal as it gets for a GUI app in Rust:

  • iced + iced_layershell: Elm-inspired retained-mode GUI (model, update, view) running on a Wayland layer-shell surface (Wayland-only, no X11)
  • fuzzy-matcher: the SkimMatcherV2 algorithm, the same engine behind the skim fuzzy finder
  • freedesktop-desktop-entry + xdg: parse .desktop files and resolve XDG base directories
  • rust-embed: compile SVG/PNG icons directly into the binary so they're available even when the system icon theme is missing an entry
  • std::process::Command: spawn the selected app and immediately exit

Why these and not the obvious alternatives?

iced over egui, slint, or GTK: The Elm architecture (model → update → view) maps cleanly onto a single-purpose tool with minimal dynamic state. iced_layershell gives a Wayland layer-shell surface with no X11 dependency baked in. GTK would have pulled in a large runtime and a lot of indirection I didn't need. egui's immediate-mode approach felt like overkill for something that only updates on keypress.

SkimMatcherV2 over substring or regex: Score-based ranking with consecutive-match bonuses makes results feel smart rather than mechanical. Typing "fire" surfaces Firefox first, not just anything containing those four letters in any order. Exact substring matching would need manual ranking logic bolted on top, at which point you're implementing fuzzy matching anyway.

rust-embed over runtime asset loading: Compiling the icons into the binary means single-file deployment with no asset path confusion and no breakage when the launcher is invoked from a keybind with a weird working directory. The binary is larger as a result (25MB), but that tradeoff is easy to accept for a tool you open thousands of times.

Here's the actual search filter from app.rs:

fn apply_filter(state: &mut Trebuchet) {
    if state.query.is_empty() {
        state.filtered = (0..state.apps.len()).collect();
    } else {
        let matcher = SkimMatcherV2::default();
        let mut scored: Vec<(usize, i64)> = state
            .apps
            .iter()
            .enumerate()
            .filter_map(|(i, app)| matcher.fuzzy_match(&app.name, &state.query).map(|s| (i, s)))
            .collect();
        scored.sort_by(|a, b| b.1.cmp(&a.1));
        state.filtered = scored.into_iter().map(|(i, _)| i).collect();
    }
    if !state.query.is_empty() && !state.filtered.is_empty() {
        state.selected = Some(0);
    } else {
        state.selected = None;
    }
}

Each keypress re-scores all app names against the current query and sorts by score descending. The skim algorithm naturally rewards consecutive and prefix matches, so typing "fire" surfaces Firefox above anything that merely contains those letters scattered across the name.

What It Does (and Doesn't)

The launcher does exactly what I wanted and nothing more. I open it with a keybind, type a few characters, hit enter, and the app opens. Closing without selecting does nothing.

  • 24ms cold start (measured with a small bash script)
  • 25MB binary, with all icons compiled in via rust-embed

Neither number is surprising given the stack, but good to have confirmed.

What it doesn't do: remember history, weight frequently used apps, act as a file browser or calculator. All deliberate omissions. If I ever want frecency ranking I'll add it then.

The part I'm most happy with is the icons. Trebuchet sources them from multiple places: bundled SVGs compiled into the binary, the system icon theme, and absolute paths from .desktop files. SVGs are preferred over rasters. On a high-DPI monitor the difference is noticeable: every icon is crisp and correctly sized, no blurry upscaled PNGs. It's a small thing, but it's the kind of polish that makes a tool feel finished.

The window is fully transparent, so it sits cleanly over any desktop without fighting the theme. Keybindings are configured in your compositor. A single line in hyprland.conf is all it takes to bind it to a key.

What Made It Hard

The fast parts were genuinely fast. But a few things took longer than expected and are worth being honest about.

iced_layershell is young. The documentation is sparse, and the API has the kind of rough edges you'd expect from a crate that's still finding its shape. Getting the surface positioned and sized correctly meant reading the source code rather than the docs, which is fine but slower. If you're building on top of it, budget time for that.

iced's message-passing model takes adjustment. Coming from an imperative background, thinking in terms of Message enums and a pure update function is a real mental shift. You can't just reach into state and change it; every interaction has to become a message, and every state change has to flow through one function. The discipline pays off (the code stays clean and predictable), but the first hour or two of fighting the model is real.

Icon resolution edge cases. System icon theme lookup sounds simple until you're actually doing it. Themes inherit from parent themes. Icon sizes matter: requesting a 48px icon when only 256px is available might or might not give you something usable. Some .desktop files embed absolute icon paths, some use bare icon names, some have no icon at all. Getting graceful fallbacks that cover all those cases without crashing or rendering blank squares took several iterations to get right.

Hours vs. Weeks

The honest version of this story without Claude Code: trebuchet never gets built. Not because it's technically out of reach, but because the research overhead would have kept pushing it to "next weekend." The Wayland ecosystem in Rust is still young, and finding the right crates, understanding how layer-shell works, learning iced's architecture: each of those is a real time cost that adds up fast for a personal project with no deadline.

A few hours is a fundamentally different category than a few weeks. It means you can actually finish things. Scratch your own itches. Build tools that fit exactly how you work, instead of settling for something close enough.

The dynamic I found most useful: an AI coding assistant is fastest when the problem is well-scoped. "Parse .desktop files and return a list of app entries" gets an accurate result immediately. The architecture (what modules to split things into, which trade-offs to make) still needs a human. But the gap between a decision and working code is now almost nothing. That's what makes the difference.

Trebuchet does exactly what I needed: open fast, filter accurately, launch the app, get out of the way. No config file, no theming story to maintain, no features I'll never use. It fits my setup because I built it for my setup, and it took an afternoon instead of a backlog item that ages forever.

That speed comes with a catch. The first version of Trebuchet had unnecessary coupling that looked fine in isolation but would have gotten painful quickly if I kept building on it the same way. The LLM doesn't know what the codebase will look like in three features. It solves the problem in front of it, and it does that well. But vibe coding stacked on top of vibe coding compounds. Left unchecked, you end up with something that works but that nobody, including you, wants to touch.

So at some point you have to slow down, read the code as if you didn't write it, and fix what doesn't hold up. Enforce a consistent pattern. Rewrite the bits that grew organically into something harder to follow than they need to be. Think of it less as cleanup and more as the part of the process that keeps the next session from being slower than the last.

The code is on GitHub. Take a look, open an issue, send a PR. Most of the stack here (iced, Wayland, the freedesktop ecosystem) was new territory for me, so if you see a better way to do something I'd be glad to hear it.
