Frankenstein's Monster: Wiring Claude Code and OpenCode Together

March 2026 8 min read

Claude plans. OpenCode executes. You drink coffee.

The Idea

Claude Code is great at understanding context, decomposing problems, and reviewing code. OpenCode is great at hammering out implementations autonomously. What if you could use them together — Claude as the architect, OpenCode as the builder?

That's what /delegate does. Type /delegate refactor the auth module to use JWTs and Claude will:

  1. Plan — break the task into discrete subtasks and ask you to approve them
  2. Delegate — run each subtask through OpenCode via an MCP tool
  3. Review — read the diff, check for bugs and gaps, report back

How Claude Code Skills Work

Claude Code has a skill system (formerly called "custom commands"). A skill is a directory with a SKILL.md file inside it. Skills live in:

  • ~/.claude/skills/<name>/SKILL.md — personal, available across all projects
  • .claude/skills/<name>/SKILL.md — project-level

The SKILL.md has a YAML frontmatter block followed by markdown instructions. When you type /skill-name, Claude reads those instructions and follows them. The $ARGUMENTS placeholder gets replaced with whatever you typed after the skill name.

Key frontmatter fields used here:

disable-model-invocation: true   # only triggers when you explicitly type /delegate
allowed-tools: mcp__run-local__run_local, Bash(git *), Read, Glob, Grep

disable-model-invocation: true is important — it prevents Claude from auto-triggering the skill based on context. You want to be the one deciding when to hand off to OpenCode.

allowed-tools scopes what Claude is allowed to do while running the skill. In this case: call the run_local MCP tool to invoke opencode, run git commands, and read files for the review phase. Claude can't write files itself — that's OpenCode's job.

The Skill File

Location: ~/.claude/skills/delegate/SKILL.md

---
name: delegate
description: Plan a task at a high level and delegate execution to opencode
  via the run_local MCP tool, then review the results.
disable-model-invocation: true
allowed-tools: mcp__run-local__run_local, Bash(git *), Read, Glob, Grep
---

You are now in **delegate mode**. Your role is to orchestrate —
you plan and review, opencode executes locally.

## Arguments

$ARGUMENTS

Parse the arguments above:
- If they start with `--model <value>` or `-m <value>`, extract that as the model to pass.
- Otherwise, treat the full string as the task. No `--model` means use the default (ollama/qwen3:14b-32k).

## Phase 1 — Plan

Break the task into discrete, self-contained subtasks...
[Present plan, wait for approval]

## Phase 2 — Delegate

mcp__run-local__run_local(
  task="<subtask description>",
  dir="<working directory>",
  model="ollama/qwen3:14b-32k"
)

[Run sequentially, verify with git status after each, pause on failure]

## Phase 3 — Review

git diff, read changed files, report what was done and flag issues.

The three-phase structure forces Claude to stop and get your sign-off before any code gets written. You see the plan, can edit it, and only then does the execution start.

Adding Ollama as an OpenCode Provider

OpenCode uses ~/.config/opencode/opencode.json for configuration. It supports any OpenAI-compatible endpoint via the @ai-sdk/openai-compatible package.

Ollama exposes an OpenAI-compatible API at http://localhost:11434/v1, so adding it is straightforward: 

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Ollama",
      "options": {
        "baseURL": "http://localhost:11434/v1"
      },
      "models": {
        "qwen3:14b-32k": {
          "name": "Qwen3 14B (32K ctx)",
          "tools": true
        }
      }
    }
  }
}

Two things are required for tool calling to work with a local model: "tools": true in the model config, and a context window large enough for opencode's agentic prompts. Ollama defaults to 4K tokens, which is too small — tool calls start failing silently. The fix is to create a custom model variant with 32K context: 

curl -s -X POST http://localhost:11434/api/create \
  -H "Content-Type: application/json" \
  -d '{"name": "qwen3:14b-32k", "from": "qwen3:14b", "parameters": {"num_ctx": 32768}}'

Once configured, target the local model with --model ollama/qwen3:14b-32k. OpenCode will download the @ai-sdk/openai-compatible package on first use. The model running here is Qwen3 14B via a dockerized Ollama instance, exposed on port 11434.

Usage

# Delegate to opencode's default model
/delegate add pagination to the /users endpoint

# Delegate to local Qwen via Ollama
/delegate --model ollama/qwen3:14b-32k add pagination to the /users endpoint

Claude presents a numbered plan first. You can approve it, tweak it, or abort. After approval, Claude calls the run_local MCP tool for each subtask, then does a final review pass: reads the diff, checks correctness, and tells you if anything looks off.

The MCP Server

The run_local tool is backed by a small Python MCP server at ~/.claude/mcp-servers/run-local/server.py. It wraps opencode run and exposes it as a proper MCP tool.

The full server is about 80 lines. The transport layer reads newline-delimited JSON from stdin and writes responses the same way: 

stdin  = sys.stdin.buffer
stdout = sys.stdout.buffer

def send(obj):
    stdout.write(json.dumps(obj).encode() + b"\n")
    stdout.flush()

def main():
    for raw_line in stdin:
        msg = json.loads(raw_line.strip())
        method = msg.get("method")
        id     = msg.get("id")

        if method == "initialize":
            send({"jsonrpc": "2.0", "id": id, "result": {
                "protocolVersion": "2025-11-25",
                "capabilities": {"tools": {}},
                "serverInfo": {"name": "run-local", "version": "1.0.0"},
            }})
        elif method == "tools/list":
            send({"jsonrpc": "2.0", "id": id, "result": {"tools": TOOLS}})
        elif method == "tools/call":
            # ... dispatch to handle_run_local

The handle_run_local function is straightforward:

def handle_run_local(args):
    task  = args["task"]
    cwd   = args.get("dir") or None
    model = args.get("model") or "ollama/qwen3:14b-32k"

    result = subprocess.run(
        ["opencode", "run", "--model", model, task],
        capture_output=True, stdin=subprocess.DEVNULL,
        text=True, cwd=cwd, timeout=600,
    )
    return [{"type": "text", "text": result.stdout}]

Register it once using the absolute Python path:

claude mcp add run-local -s user -- /usr/bin/python3 ~/.claude/mcp-servers/run-local/server.py

This is the key architectural decision, and it's why the approach works where a plain skill didn't.

Gotchas That Led Here

1. The Background Execution Problem

The first version of /delegate called opencode run directly via Claude's Bash tool. It worked most of the time, but had a recurring failure mode: Claude would occasionally run the command with run_in_background: true. When that happened, the output got a task ID instead of inline text, and the subsequent TaskOutput call would fail with: 

Error: Task ID is required
Invalid tool parameters

The obvious fix — adding "Never use run_in_background" to the skill instructions — reduced the frequency but didn't eliminate it. Prompt rules are hints, not constraints.

The real fix was to stop using Bash for this entirely. MCP tools are always synchronous — there's no run_in_background parameter. When Claude calls mcp__run-local__run_local, it blocks until the server returns a response. The problem becomes structurally impossible.

2. The Wrong MCP Wire Format

The first MCP server implementation used Content-Length framing — the same protocol as the Language Server Protocol: 

Content-Length: 160\r\n
\r\n
{"jsonrpc": "2.0", ...}

It passed all manual tests but claude mcp list reported ✗ Failed to connect every time.

Adding a log file to the server revealed what Claude Code was actually sending:

logging.basicConfig(filename="/tmp/run-local-mcp.log", level=logging.DEBUG)

# log output:
# header line: b'{"method":"initialize","params":{"protocolVersion":"2025-11-25",...}}\n'

Claude Code 2.1.81 uses newline-delimited JSON (one JSON object per line), not Content-Length framing. It also negotiates protocol version 2025-11-25, not the older 2024-11-05. The fix was switching the transport entirely — read lines, write lines, no framing headers. Without the log, this would have been very hard to diagnose.

3. The stdin Inheritance Problem

After fixing the wire format, the server connected fine — but run_local calls would always time out after 300 seconds, even with Ollama warm and the model loaded. Running opencode run directly from the terminal worked instantly.

The culprit: subprocess.run with no stdin= argument inherits the parent process's stdin. The MCP server's stdin is the JSON protocol pipe — the same stream Claude Code uses to send tools/call requests. When opencode launched as a subprocess, it inherited that pipe and sat there reading protocol messages instead of running the task. It never produced output, so it hung until the timeout killed it. 

# Wrong — opencode inherits the MCP protocol pipe as its stdin
result = subprocess.run(
    ["opencode", "run", "--model", model, task],
    capture_output=True, text=True, cwd=cwd, timeout=300,
)

# Fixed — opencode gets /dev/null as stdin, nothing to wait on
result = subprocess.run(
    ["opencode", "run", "--model", model, task],
    capture_output=True, stdin=subprocess.DEVNULL,
    text=True, cwd=cwd, timeout=300,
)

This is easy to miss because it only manifests when the parent process has a meaningful stdin. A quick manual test of the server — where stdin is a terminal — passes fine. The bug only bites in production, where stdin is a pipe.

4. The external_directory Permission Sandbox

Even with the server fixed, writes to paths outside the working directory silently failed. The symptom looked like OpenCode ran successfully — no error, exit code 0 — but the file never appeared: 

! permission requested: external_directory (/tmp/*); auto-rejecting
✗ write failed
Error: PermissionRejectedError({"_tag":"PermissionRejectedError"})

OpenCode sandboxes tool calls by default. Any path outside the directory where opencode run was started triggers an external_directory permission check, which defaults to auto-reject in non-interactive mode. Since the MCP server spawns opencode headlessly, there's no one to approve the prompt — it just silently fails.

The fix is a one-time addition to ~/.config/opencode/opencode.json:

{
  "permission": {
    "external_directory": {
      "/**": "allow"
    }
  }
}

This tells OpenCode to allow all external paths without prompting. Scope it down if you want tighter control — e.g. "/home/spike/workspace/**": "allow" — but for a local dev setup the blanket allow is fine.

Why This Works

OpenCode's opencode run command is the key — it runs the tool non-interactively with a single message, then exits. That makes it composable. Claude can call it in a loop, pass different prompts to each invocation, and collect results.

Each opencode run call starts a fresh session, so every subtask message must be fully self-contained. Claude's planning phase handles this: the instructions explicitly say to write subtask descriptions that include file paths and enough context for OpenCode to act without history.

Small subtasks also matter more than you'd expect. A prompt that says "implement the user auth flow, add the middleware, wire up the routes, and write tests" gives OpenCode too many things to juggle at once. One of them gets half-done. Split it into four subtasks and each one completes cleanly. The overhead of more invocations is worth it.

The review phase closes the loop. Claude reads git diff, checks the changed files, and can catch things OpenCode missed — incomplete implementations, off-spec behavior, obvious bugs. If it finds issues, it asks whether to fix them directly or spin up another delegation round.
